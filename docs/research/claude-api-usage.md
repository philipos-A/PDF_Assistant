# Claude API usage in the Rust backend: claims checked against primary sources

Checked 2026-11-18 against `backend/src/claude.rs` and `backend/src/config.rs`. Sources: the `claude-api` skill (bundled reference files, cached 2026-11-03), the live docs at platform.claude.com (fetched as `.md` on the check date), and the `anthropic-sdk-python` source on `main`. Where the skill and the live docs disagree, the live docs win.

## 1. `anthropic-version: 2026-10-21` (claude.rs:18) - CONFIRMED

`2026-10-21` is a listed, current API version on the Claude API. It is the version the newest SDKs send by default. On this version, `temperature`/`top_p`/`top_k` return a 400, and a `document` block placed directly in an `assistant` message returns a 400. The code sends neither, and the PDF goes in a `user` turn. Sources: https://platform.claude.com/docs/en/api/versioning ; https://platform.claude.com/docs/en/api/migration-2026-10-21 ; skill `shared/api-version-migration.md`.

## 2. Server-side fallback (claude.rs:20, 129-133, stream parsing) - CONFIRMED, with one WRONG sub-claim

- **Header and body: CONFIRMED.** `fallbacks: "default"` needs the beta header `server-side-fallback-2026-07-01`. The older `-2026-06-01` header accepts only the array form. The feature is in beta on the Claude API. It is not available on Bedrock, Vertex AI or Foundry, and the Batches API rejects it.
- **Trigger: CONFIRMED.** Only safety-classifier declines (`stop_reason: "refusal"`) trigger a fallback. Rate limits, overloads and 5xx errors come back unchanged. On `claude-sonnet-5-5`, `"default"` retries only `cyber` and `frontier_llm` declines, on Claude Sonnet 5. Declines in `bio`, `reasoning_extraction` and `general_harms` still come back as refusals.
- **Stream marker: CONFIRMED.** There is no special SSE event. The switch arrives as an ordinary `content_block_start`/`content_block_stop` pair with `content_block.type == "fallback"`, shaped as `{"type":"fallback","from":{"model":...},"to":{"model":...},"trigger":{...}}`. Content that already streamed is never invalidated.
- **Which model answered: WRONG as implemented.** The code reads the model only from `message_start.message.model`. That value is right in two cases: a decline before any output (`message_start` waits for the fallback attempt, so it names the fallback model), and sticky routing. After a **mid-output** decline, however, `message_start` has already named the requested model. The docs say to read the serving model from the `fallback` block's `to.model`, and from the `fallback_message` entry in the final `message_delta`'s `usage.iterations`. A non-streaming response's top-level `model` is reliable. The authoritative "served by a fallback" signal is a `fallback_message` entry in `usage.iterations`; sticky turns carry no `fallback` block. Sources: https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback (sections "Server-side fallback", "What the response contains", "Streaming", "Sticky routing") ; skill `shared/model-migration.md` -> refusal section and Migrating to Claude Sonnet 5.5 -> Safeguards and fallback ; skill `shared/platform-availability.md`.

## 3. Top-level `cache_control` together with a breakpoint on the PDF block - CONFIRMED

Automatic caching is a top-level `cache_control` field on POST /v1/messages. It places the breakpoint on the last cacheable block and moves it forward as the conversation grows. It is compatible with explicit block-level breakpoints and uses one of the 4 slots. It returns a 400 only in two cases: all 4 slots are already used, or an explicit marker on the last block has a different TTL. Neither applies here, because there is one explicit marker on the PDF and both use the default 5-minute TTL. Automatic caching is available on every platform except legacy Bedrock `bedrock-runtime`. The system prompt comes before the PDF, so the PDF marker caches system + PDF together. Sources: https://platform.claude.com/docs/en/build-with-claude/prompt-caching ("Automatic caching", "Automatic caching is compatible with explicit cache breakpoints") ; skill `shared/prompt-caching.md` -> Automatic vs explicit breakpoints.

## 4. `output_config: {effort: "medium"}` on `claude-sonnet-5-5` - CONFIRMED

Effort is GA and goes inside `output_config`. Claude Sonnet 5.5 supports all five levels: `low`, `medium`, `high`, `xhigh`, `max`. Its default is `high`, and its levels are recalibrated relative to Claude Sonnet 5, so `medium` is a valid, explicit step-down. Note: if `CLAUDE_MODEL` is changed to Claude Opus 5.5 or Claude Haiku 5.5, `medium` is already their default. The env var is not validated against these five values; an invalid value returns a 400. Sources: https://platform.claude.com/docs/en/build-with-claude/effort ("Effort levels", "Recommended effort levels") ; skill SKILL.md -> Thinking & Effort table.

## 5. Model `claude-sonnet-5-5` and `max_tokens: 16000` - CONFIRMED

`claude-sonnet-5-5` is the current Sonnet. It is listed as Active, with a 1M context window and 128K max output. 16,000 is well within the limit. The skill suggests about 64,000 for streaming requests so long answers are not cut off. That is a recommendation, not a limit. Sources: https://platform.claude.com/docs/en/about-claude/models/overview ; skill `shared/models.md` (row `claude-sonnet-5-5`, Active) ; skill SKILL.md -> Common Pitfalls (`max_tokens` defaults).

## 6. Errors, refusals and retries - mostly CONFIRMED; the retry-after cap is WRONG

- **Mid-stream `error` event: CONFIRMED.** The API can send `event: error` / `{"type":"error","error":{"type":"overloaded_error",...}}` after a 200 response, which corresponds to an HTTP 529. Source: https://platform.claude.com/docs/en/build-with-claude/streaming#error-events ; https://platform.claude.com/docs/en/api/errors.
- **HTTP 529: CONFIRMED.** 529 `overloaded_error` means "The API is temporarily overloaded" (high traffic across all users) and can be retried. Source: https://platform.claude.com/docs/en/api/errors ; skill `shared/error-codes.md`.
- **`stop_reason: "refusal"`: CONFIRMED.** A refusal is a normal HTTP 200 with `stop_details.category`. It can arrive before any output or mid-stream. The docs say to treat partial output as incomplete and discard it. The backend has already forwarded those deltas when it emits its error, so the frontend must drop the partial answer. Source: https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback.
- **Retryable set 408/409/429/5xx: CONFIRMED.** The official SDK retries 408, 409, 429 and >=500, as well as connection errors, with 2 retries by default. It applies exponential backoff from 0.5 s, capped at 8 s, with jitter. A response header `x-should-retry: true|false` overrides the decision; the code ignores it. A spend-cap 429 has no `retry-after` and keeps failing until access resumes. Sources: `anthropic-sdk-python` `src/anthropic/_base_client.py` (`_should_retry`, `_calculate_retry_timeout`) and `_constants.py` ; https://platform.claude.com/docs/en/api/errors.
- **Capping `retry-after` at 10 s: WRONG (deviates from the recommendation).** The docs say the SDK retries "honoring the `retry-after` header when present". The Python SDK waits the full value the server sends; its only upper bound is a platform sleep limit, about 49 days. It also reads `retry-after-ms` first and accepts an HTTP-date form. Clamping to 10 s retries earlier than the server asked, which burns retries on rate-limited requests. Sources: as above (`_parse_retry_after_header`).

## 7. PDF limits vs `max_upload_mb=24`, `max_pages=600` - CONFIRMED (the 32 MB premise is WRONG)

- **Request size: 32 MB is outdated.** The live docs give a 128 MB maximum request size for the Messages API on the first-party Claude API; Batch is 256 MB and Files is 500 MB. Other platforms have different limits. The skill's cached quick reference still says 32 MB, which is stale. A 24 MB PDF grows to about 32 MB after base64 encoding, which is well under 128 MB, so the default is safe. Oversized requests get a 413 `request_too_large`, which Cloudflare returns before the request reaches the API.
- **Pages: CONFIRMED.** The limit is 600 pages per request, or 100 when the request's context window is under 1M tokens. `claude-sonnet-5-5` has 1M, so 600 is correct. If `CLAUDE_MODEL` is set to a model with less than 1M context (e.g. `claude-haiku-4-5`, 200K), the limit is 100. Dense PDFs can also fill the context window before they reach the page limit. Sources: https://platform.claude.com/docs/en/build-with-claude/pdf-support ; https://platform.claude.com/docs/en/api/errors#request-size-limits ; skill SKILL.md -> Document & File Input (stale 32 MB figure).

## Recommended code changes (WRONG items only)

1. **Done.** **Serving model after a mid-output fallback** (claude.rs, `content_block_start` arm): when `content_block.type == "fallback"`, set `model` from `content_block.to.model`. Optionally, also check `message_delta.usage.iterations` for a `fallback_message` entry and report a `served_by_fallback` flag in the `done` event.
2. **Done (fails fast above 10 s instead of waiting).** **Honor `retry-after` fully** (claude.rs `retry_delay`): remove the 10 s clamp. If the wait must be bounded for UX, fail fast with the rate-limit message when `retry-after` exceeds the bound, rather than retrying early. Also read `retry-after-ms` first, and respect `x-should-retry` in `retryable`.
3. **Comments/docs only:** any mention of a 32 MB request limit should say 128 MB (first-party API). No change to `max_upload_mb=24` is needed.

## 8. Files API and citations (added 2026-11-23) - CONFIRMED

Checked against the live docs on 2026-11-23 before adding both to `claude.rs`.

- **Files API is GA: CONFIRMED.** Upload with `POST /v1/files` as multipart form data, field `file`, with only `x-api-key` and `anthropic-version`. No beta header: `files-api-2025-04-14` is optional and only changes list/metadata shapes. The response `id` is the `file_id`. A PDF is referenced as `{"type": "document", "source": {"type": "file", "file_id": "..."}}`, and `cache_control` and `citations` work on that block as on a base64 one. Files persist until deleted (`DELETE /v1/files/{file_id}`) unless uploaded with `expires_in_seconds`; the code sets no expiry. Files are workspace-scoped, so file ids stay server-side and are never accepted from the browser. A file that doesn't exist gives a 404 `not_found_error` ("File `file_...` not found."); the backend treats a 404 whose message mentions a file as "upload again". Upload limit is 500 MB per file; uploads, deletes and listing are free, and file content in Messages is billed as input tokens. Available on the Claude API, Claude Platform on AWS, Claude Models on Google Cloud (Anthropic managed) and Microsoft Foundry (hosted on Anthropic), but not on Bedrock or Vertex AI, which is why `USE_FILES_API` can be turned off and a failed upload falls back to base64. Source: https://platform.claude.com/docs/en/build-with-claude/files
- **Citations: CONFIRMED.** Enabled per document block with `citations: {"enabled": true}` (all document blocks or none). PDF citations are `page_location` objects: `cited_text`, `document_index`, `document_title`, `start_page_number` (1-indexed) and `end_page_number` (**exclusive**; the backend converts it to an inclusive last page). In a stream they arrive as `content_block_delta` events with `delta.type == "citations_delta"`, each carrying one `citation` for the current text block. `cited_text` doesn't count toward output tokens, or toward input tokens when passed back; the backend sends earlier answers back as plain text anyway. Citations work with prompt caching (cache the document block) and are incompatible with `output_config.format`, which this app doesn't use. Scanned pages without extractable text can't be cited. Source: https://platform.claude.com/docs/en/build-with-claude/citations

## 9. OpenRouter fallback (added 2026-11-24) - CHECKED

Checked against the OpenRouter docs on 2026-11-24 before adding `backend/src/openrouter.rs`. Sources: https://openrouter.ai/docs/api-reference/chat-completion ; https://openrouter.ai/docs/api-reference/streaming ; https://openrouter.ai/docs/guides/routing/model-fallbacks.md ; https://openrouter.ai/docs/features/multimodal/pdfs ; https://openrouter.ai/docs/api-reference/errors ; https://openrouter.ai/docs/api-reference/authentication ; model ids, prices and `input_modalities` from `GET https://openrouter.ai/api/v1/models`.

- **Request:** `POST https://openrouter.ai/api/v1/chat/completions`, `Authorization: Bearer <key>`. `HTTP-Referer` and `X-Title` are optional and not sent.
- **Model fallback:** `models: [...]` is tried in order. Any error can move on to the next model, including rate limits and downtime. The chunk's top-level `model` names the model that answered. If all fail, the last error comes back.
- **PDF:** a chat-completions content part `{"type":"file","file":{"filename":...,"file_data":"data:application/pdf;base64,..."}}`. With no `plugins`, OpenRouter uses the model's native file input, else `mistral-ocr` (paid). The default models all list `file` in `input_modalities`. No size limit is documented beyond a generic 413.
- **Stream:** `data: {json}` frames, `: OPENROUTER PROCESSING` comments, a final `data: [DONE]`. `finish_reason` is on the last content chunk; `usage` (`prompt_tokens`, `completion_tokens`) is on a final chunk. A mid-stream error keeps HTTP 200 and sends a chunk with `error: {code, message}` and `finish_reason: "error"`.
- **Errors:** `{"error": {"code", "message", "metadata"}}`; 401 bad key, 402 insufficient credits, 429 rate limited, 502 model down, 503 no provider available.
- **Reasoning:** `reasoning: {effort}` (`minimal` to `max`) shares `max_tokens` with the answer; a budget that runs out ends with `finish_reason: "length"`.
- **Not verified:** whether `reasoning.effort` changes anything for every Gemini model (OpenRouter documents `reasoning.max_tokens` for Gemini thinking). The request sends `effort` only.
